LangChain 1.x Capstone – E‑commerce Support Agent

Purpose of this document

This document is the requirements and specification for your LangChain 1.x capstone project. It describes what you must build (functional requirements), the target architecture (agent + tools), data and persistence expectations, and non‑functional guidelines. Use it as your single source of truth while designing and implementing the project.

1. Project Overview

You will build an AI‑powered customer support chatbot for a fictional e‑commerce application, using LangChain 1.x, Streamlit, and an SQLite database. The project must demonstrate:

  • A single conversational agent in LangChain 1.x that orchestrates all logic using tools.
  • A Streamlit UI for both customers and a simple admin view.
  • SQL‑backed queries and updates for orders, returns, tickets, and email logs.
  • A RAG component using ChromaDB for policy/FAQ questions.
  • Persistent conversation state using a LangChain checkpointer (not SQL).
  • Gmail integration for notifications: use LangChain’s GmailToolkit by default, or optionally a Gmail MCP server via langchain-mcp-adapters.
  • Basic logging and observability via LangChain 1.x callbacks / middleware.

2. Roles and User Journeys

2.1 Customer

A customer interacts with the system as follows:

  • Logs in using email and password (for this project, plain‑text passwords are acceptable).
  • Starts a new conversation from the Streamlit UI (generates a new UUID conversation id).
  • Asks the chatbot questions about:
    • Orders, returns, payments, and general account queries (SQL‑backed).
    • Policies such as return rules, refund timelines, and shipping details (RAG‑backed).
  • Requests order cancellation where allowed by business rules.
  • Requests a return for one or more items in an order.
  • Receives email notifications (via Gmail) when:
    • An order is cancelled.
    • A return request is created and a ticket is opened.

2.2 Admin

An admin has a simple management view:

  • Logs in using a dummy admin email + password stored in the database.
  • Opens an admin Streamlit page to:
    • View all return tickets (PENDING / APPROVED / REJECTED).
    • Filter by status, customer email, or date (simple filters are sufficient).
    • Approve, edit, or reject each return request.
  • When acting on a ticket, the system should be able to:
    • Use the stored user email and conversation id (UUID) to resume the original conversation thread in the checkpointer.
    • Let the agent use its tools to complete any follow‑up actions (e.g., update status, send emails).
Human‑in‑the‑loop

The chatbot must not auto‑approve returns. It can only create a return + ticket and inform the user that a human will review the request. The admin makes the final decision.

3. Functional Requirements

3.1 Authentication

  • Customer login using user_email and password (plain‑text allowed for this lab).
  • Admin login using a dummy admin email and password.
  • user_email is the only user identifier you should use in your application logic and tools.

3.2 Customer Chatbot UI (Streamlit)

  • A login screen for email/password authentication.
  • After login, a chat screen with:
    • A button to start a new conversation (generates a new UUID conversation_id).
    • A visible chat history for the current conversation.
    • A text input for the next user message.
  • On each message:
    • Call the single LangChain agent, passing user_email and conversation_id so the checkpointer can load the correct state.
    • Render the agent’s response in the chat UI.

3.3 Capabilities of the Chatbot

  • Data questions (SQL):
    • “Show my last 5 orders.”
    • “What is the status of order #123?”
    • “List all my returned orders.”
    • “How much did I spend in the last month?”
  • Actions (SQL + business rules):
    • Cancel an order if allowed (status, dates, etc.).
    • Create a return request for order items and open a ticket.
  • Policy questions (RAG):
    • “What is your returns policy?”
    • “Within how many days can I return an item?”
    • “How long do refunds take?”
    • “Do I pay for return shipping?”

3.4 Admin Dashboard

  • Login page for admin email/password.
  • Dashboard listing:
    • All return tickets with status and key fields (subject, user email, order id, conversation id, timestamps).
    • Filters by status and (optionally) by user_email or date.
  • Admin can approve, edit, or reject a return:
    • Updates the ticket and return status in the database via the agent’s SQL tools.
    • Should allow resuming the original conversation (via user_email + conversation_id) if you choose to show a follow‑up message to the customer later.

4. Agent and Tools (LangChain 1.x)

4.1 Single Main Agent

  • You must implement one main conversational agent using LangChain 1.x.
  • This agent is responsible for:
    • Interpreting every user/admin message.
    • Deciding which tools to call and in what order.
    • Combining SQL results, RAG outputs, and email operations into coherent responses.
  • You should not create multiple cooperating agents for this project (that can be a later extension).

4.2 Tool 1 – SQL Toolkit (Business Database Operations)

  • Use LangChain 1.x SQL support (SQLDatabase + SQLDatabaseToolkit or equivalent).
  • Let the agent dynamically generate SQL to:
    • Query orders, order_items, payments, returns, tickets, and email_logs for a given user_email.
    • Create or update rows for returns and tickets, including storing user_email and conversation_id on each ticket.
    • Apply business rules such as “order must be in PLACED/SHIPPED to be cancelled”.
  • Do not write many manual helpers like get_orders_for_user(); rely on the toolkit.

4.3 Tool 2 – RAG Policy Search (rag_policy_search)

  • Implement a single custom RAG tool that:
    • Uses a ChromaDB retriever over: returns_policy.txt, shipping_policy.txt, faq_returns_and_cancellations.txt.
    • Accepts the user’s question as input.
    • Returns top‑k relevant chunks or a structured summary.
  • Describe this tool so the agent understands it is for policy/FAQ questions only, not for user‑specific data.

4.4 Tool 3 – Gmail Email Notification (send_gmail_notification)

Create a single custom tool send_gmail_notification that the agent calls whenever a customer notification is needed (cancellation confirmed, return ticket created, or return status updated). The agent should see one notification tool, regardless of which send backend you use underneath.

The tool must:

  • Send an email to the customer’s user_email with a clear subject and body.
  • After a successful send, use the SQL toolkit to write a row into email_logs with user_email, email type, subject, and timestamp.
  • On failure, log the error (via middleware) and tell the agent so it can inform the user that the email could not be sent.

Implement the send path with one of the two backends below. Choose the backend with a configuration switch such as GMAIL_BACKEND=toolkit (default) or GMAIL_BACKEND=mcp. Document your choice in the README.

Option A (default) – LangChain GmailToolkit

  • Use LangChain’s GmailToolkit (for example from langchain_google_community / langchain_community.agent_toolkits) as the send backend. This matches the Gmail HITL lab.
  • Wrap the toolkit’s send tool (e.g. GmailSendMessage) inside send_gmail_notification. Do not expose the full toolkit (search, draft, trash) to the support agent unless you have a clear reason.
  • Load Gmail OAuth credentials from environment variables and files such as credentials.json / token storage — never hard‑code secrets.

Option B – Gmail MCP server

  • Connect to a Gmail MCP server using langchain-mcp-adapters and MultiServerMCPClient, as taught in the MCP module.
  • Map the MCP server’s send tool (typically send_email) into send_gmail_notification so the agent still has a single notification tool.
  • Do not dump every Gmail MCP tool (search, delete, labels, etc.) onto the support agent. Notification send is the required capability.
  • Configure the MCP connection (stdio command/args, or a streamable HTTP URL) via environment variables, not hard‑coded paths.
  • After a successful MCP send, still write email_logs via the SQL toolkit — MCP does not replace the business database log.
Backend choice

GmailToolkit is the default and is enough to pass the capstone. Use the Gmail MCP server if you want to practise wiring MCP tools into a LangChain 1.x agent. Either way, the agent’s public tool remains send_gmail_notification, and every sent mail must appear in email_logs.

Key point

Your agent + tools should handle almost all business logic. Your Streamlit and service code should be thin wrappers that pass context to the agent and render its responses.

5. Data, Persistence, and Conversation Identity

5.1 SQLite Business Database

You will be given a ready‑made SQL script in the project directory (for example, ecommerce_setup.sql) that creates an ecommerce.db SQLite database with tables such as:

  • users – stores email, password, full_name, and role.
  • products, orders, order_items, payments.
  • returns – stores per‑item returns with status PENDING/APPROVED/REJECTED.
  • tickets – stores return tickets and includes:
    • user_email – login email of the customer.
    • thread_id (conversation UUID) – used to resume the correct conversation thread.
  • email_logs – stores emails sent (recipient, subject, type, timestamp).

5.2 Conversation State and Checkpointer

  • Use a persistent LangChain 1.x checkpointer (file/SQLite/other) to store conversation history.
  • Each conversation must be uniquely identified by:
    • user_email – email used for login.
    • conversation_id – a UUID generated when the user starts a new conversation.
  • The pair (user_email, conversation_id) is the logical “thread id” you pass to the checkpointer.
  • Do not store chat transcripts in SQL; SQL is for business data only.

6. RAG Knowledge Base

A small, curated policy knowledge base is provided as three text files in the project folder:

  • returns_policy.txt
  • shipping_policy.txt
  • faq_returns_and_cancellations.txt

You must load, chunk, and embed these documents into a ChromaDB collection and expose them via the rag_policy_search tool described earlier. The agent should use this tool only for policy/FAQ questions and continue to use SQL tools for user‑specific questions.

7. Logging and Observability

  • Implement logging using LangChain 1.x callbacks / middleware, not custom decorators.
  • Attach middleware to:
    • The main agent runnable.
    • SQL toolkit operations.
    • RAG tool and Gmail notification tool invocations (whether backed by GmailToolkit or the Gmail MCP server).
  • Each log entry should include:
    • Timestamp.
    • user_email (if available).
    • Tool or action name.
    • Short summary of inputs (e.g., order id, return id).
    • Success / failure and any error messages.
  • Write logs to logs/app.log using Python’s logging module.

8. Suggested Project Structure (Agent‑Centric)

You may adapt this structure, but keep your design agent‑centric:

  • pyproject.toml, uv.lock – dependencies (Streamlit, LangChain 1.x, Chroma, and either Gmail toolkit packages or langchain-mcp-adapters if you use MCP).
  • src/app_customer.py – Streamlit app for customer chat.
  • src/app_admin.py – Streamlit app for admin dashboard.
  • src/config.py – configuration and environment loading.
  • src/auth.py – simple login helpers using user_email and password.
  • src/agents.py – single main agent, SQL toolkit, rag_policy_search, and send_gmail_notification, plus checkpointer wiring.
  • src/gmail_backend.py (optional) – select GmailToolkit or Gmail MCP from GMAIL_BACKEND and return the send helper used by send_gmail_notification.
  • src/logging_middleware.py – LangChain callback / middleware definitions.
  • src/db_init.py (optional) – helper to initialise ecommerce.db using the notebook logic.
  • logs/app.log – log output from your middleware.

9. Non‑Functional Requirements and Expectations

  • Use uv to manage a clean Python environment and dependencies.
  • Do not hard‑code API keys, Gmail OAuth secrets, or MCP connection strings in code; use environment variables and a .env / configuration layer (including GMAIL_BACKEND=toolkit or GMAIL_BACKEND=mcp).
  • Document any simplifications (e.g., plain‑text passwords, minimal validation) clearly in your README.
  • Prioritise clarity, agent‑centric design, and correctness over adding many extra features.

10. Application flow diagrams (customer vs admin)

These diagrams summarize the end‑to‑end journey after a successful login for each role. They align with an agent‑centric design: Streamlit is a thin shell; the same main agent (LangChain 1.x / LangGraph with tools + checkpointer) carries out SQL, RAG, Gmail, and guarded actions. A typical lab layout runs the customer UI and admin UI as two Streamlit processes (for example ports 8501 and 8502). The logical conversation thread is keyed by user_email and conversation_id (often composed into one checkpointer thread id).

10.1 Customer flow (after login)

Customer authenticates against users in ecommerce.db, starts or selects a chat (new conversation_id UUID when starting fresh), then each message invokes the agent with that thread context. Read‑only questions use the SQL toolkit and/or rag_policy_search. Cancellations and returns require human approval: the agent may notify by email, then pauses until an admin resumes the same thread.

flowchart TD A[Customer opens chat app e.g. app.py] --> B[Login: email + password] B --> C{Valid user in SQLite users?} C -->|No| B C -->|Yes; role customer| D[Session: user_email + conversation_id UUID] D --> E{Start new conversation?} E -->|Yes| F[New conversation_id] E -->|No| G[Keep current thread] F --> G G --> H[User sends chat message] H --> I[Invoke main agent with thread key user_email + conversation_id] I --> J[Middleware logging] J --> K{Agent chooses tools} K -->|Policy / FAQ| L[rag_policy_search ChromaDB] K -->|Orders, spend, status| M[SQL toolkit on ecommerce.db] K -->|Cancel or return request| N[Gmail notify if needed then action tools] L --> O[Assistant message] M --> O N --> P{Human-in-the-loop interrupt?} P -->|Yes| Q[Persist pending ticket / pending action + thread reference] P -->|No| R[Commit business updates e.g. order or return rows] Q --> S[User sees pending human review message] R --> O S --> O O --> T[Checkpointer saves conversation state not business chat in SQL] T --> H

10.2 Admin flow (after login)

Admin authenticates with an admin account in users, then uses a dashboard (e.g. app_admin.py) to list open return/cancel work. Decisions resume the customer’s paused agent thread so tools can finish SQL updates and confirmation emails; tickets and email_logs reflect the outcome.

flowchart TD A[Admin opens dashboard e.g. app_admin.py] --> B[Login: admin email + password] B --> C{Valid user role admin?} C -->|No| B C -->|Yes| D[Load services e.g. RAG + Gmail for resumed agent] D --> E[Query tickets / pending actions for PENDING items] E --> F{Any items to review?} F -->|No| G[Show empty queue; refresh when customers submit] F -->|Yes| H[Show filters: status, customer email, date] H --> I[Admin opens item: user_email, order, conversation/thread id] I --> J{Decision} J -->|Approve| K[Resume agent thread: approve] J -->|Reject| L[Resume agent thread: reject] J -->|Edit details| M[Apply edits then approve/reject via agent tools] K --> N[Agent completes SQL updates returns tickets orders] L --> N M --> N N --> O[Optional Gmail + write email_logs] O --> P{Another interrupt on same thread?} P -->|Yes| E P -->|No| Q[Dashboard refreshes list] Q --> E
How the two flows connect

The customer chat and admin dashboard are separate UIs, but they coordinate through shared persistence: business data in ecommerce.db (orders, returns, tickets, optional pending_actions) and conversation state in the LangChain checkpointer using the same thread identity the ticket stores (user_email and conversation UUID). That lets an admin decision pick up exactly where the customer’s agent run paused.
